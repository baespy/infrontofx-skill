# Think First

ใช้ก่อนเขียนระบบใหม่ ก่อนรีไรต์ resource ที่ยังไม่เคยอ่าน และเมื่อโจทย์อ่านได้มากกว่าหนึ่งทาง งานที่โจทย์ครบอยู่แล้วไม่ต้องผ่านไฟล์นี้

## อ่านก่อนถาม

1. อ่านทุกไฟล์ของ resource ที่เกี่ยว: `fxmanifest.lua`, config, core และหน้าเว็บ
2. หาผู้เรียกจากนอก resource ด้วยคำสั่งใน `references/plan.md` แล้วเก็บรายการสัญญาเดิมด้วยคำสั่งใน `references/verify.md`
3. เปิด `PROGRESS.md` ของเจ้าของ และ `memory/` ของ infrontofx ดูว่าเรื่องนี้เคยตัดสินไว้แล้วหรือยัง
4. หา resource [1nfx] ที่ผ่านมาตรฐานแล้วและทำงานคล้ายกัน ใช้เป็นแบบ ไม่คิดโครงใหม่เอง

ข้อเท็จจริง (ไฟล์ไหน ใครเรียก ค่าเท่าไร) ต้องหาเอง ห้ามถามเจ้าของ ส่วนสิ่งที่ผู้เล่นควรเห็นเป็นการตัดสินใจของเจ้าของ

## ถามเมื่อไร

ถามเฉพาะเรื่องที่ทำให้ของที่สร้างออกมาต่างกันจริง และโจทย์ ของเดิม `memory/` หรือ `PROGRESS.md` ไม่ได้บอกไว้

| ถาม | ไม่ถาม ตัดสินเองตามมาตรฐาน |
| --- | --- |
| เก็บถาวรใน DB หรือหายเมื่อออกเกม | ชื่อไฟล์ การแตกไฟล์ใน core |
| ใครใช้ได้ ทุกคน job ไหน หรือแอดมิน | ใช้ส่วนไหนของ `1nfx_lib` |
| ทุกคนเห็น หรือเฉพาะคนในโซนหรือ bucket เดียวกัน | ช่วง `Wait`, การรวม loop, การ cache |
| ราคา รางวัล cooldown ที่ทั้งโจทย์และของเดิมไม่มี | ชื่อ event, ชื่อ method, รูปแบบ NUI |
| UI ใหม่ยึดหน้าตาของ UI ตัวไหน เมื่อมีหลายแบบให้เลือก | สไตล์โค้ดและวิธี optimize |

กติกาการถาม:

1. ไม่เกิน 3 ข้อในข้อความเดียว เรียงเลขข้อ
2. ทุกข้อมีคำตอบที่แนะนำ เจ้าของตอบ "ใช่" คำเดียวแล้วใช้ที่แนะนำได้ทุกข้อ
3. ระหว่างรอ ทำส่วนที่ไม่ขึ้นกับคำตอบไปก่อน (สำรอง อ่าน วางโครง เขียนสเปกส่วนที่ชัดแล้ว)
4. เรื่องที่ไม่ถึงขั้นต้องถาม เขียน `สมมติ: ...` บรรทัดละข้อไว้ต้นรายงานแล้วทำต่อ เจ้าของแก้ได้ในประโยคเดียว
5. ถามเกิน 3 ข้อได้เฉพาะเมื่อเจ้าของสั่ง "ถามให้สุด" หรือ "ซักมาเลย" ให้ถามเป็นรอบ แต่ละรอบถามทุกข้อที่ข้อที่มันขึ้นอยู่ได้คำตอบแล้ว จนไม่เหลือข้อที่ต้องเดา

```text
1. รางวัลรายวันเก็บลง DB ถาวร หรือหายเมื่อออกเกม? แนะนำ: ถาวร ตาราง <resource>_claims
2. รับได้ทุกคน หรือเฉพาะบาง job? แนะนำ: ทุกคน
3. ประกาศให้ทุกคนเห็นตอนมีคนได้รางวัลใหญ่ไหม? แนะนำ: ไม่ประกาศ แจ้งเฉพาะคนที่ได้
ตอบ "ใช่" = ใช้ที่แนะนำทุกข้อ
```

## โจทย์อ่านได้สองทาง

วางทั้งสองทาง ทางละบรรทัด พร้อมสิ่งที่ผู้เล่นเห็นต่างกัน แล้วบอกทางที่แนะนำ ถ้าของเดิมหรือ `memory/` ตัดสินไว้แล้ว ใช้ตามนั้นและบอกในรายงานโดยไม่ถาม

## สเปกระบบใหม่

เขียนจากโจทย์และของที่อ่านมา ไม่สัมภาษณ์เจ้าของ เก็บที่ `<project>/_dev/<YYYY-MM-DD>/<resource>/spec.md` (ไม่อยู่ในโฟลเดอร์ resource) แล้วใช้เป็นต้นทางของ `references/plan.md`

```markdown
# <resource>

หน้าที่: <หนึ่งประโยคที่ผู้เล่นเข้าใจ>

## ผู้ใช้
- ผู้เล่น: ทำอะไร เห็นอะไร
- job หรือแอดมิน: ได้สิทธิ์อะไรเพิ่ม

## server ตัดสิน
| ค่า | ตรวจที่ | กันซ้ำ |
| --- | --- | --- |
| ราคา ของ รางวัล cooldown ระยะ bucket | handler ฝั่ง server ตรงจุดรับ | throttle ต่อ src และ lock ระหว่าง await |

## event และ callback
| ชื่อ | ทิศ | payload | ใครยิง | ความถี่ |
| --- | --- | --- | --- | --- |
| scriptname .. ":SV:claim" | client -> server | { id } | ผู้เล่นกดรับ | ตามคลิก throttle 1 วินาที |
| scriptname .. ":getState" (lib.callback) | ไป-กลับ | {} -> { claimed, nextAt } | เปิดเมนู | หนึ่งครั้งต่อการเปิด |

## export
- ให้: ชื่อ พารามิเตอร์ ค่าที่คืน
- ใช้: <resource>:<export>

## DB
| ตาราง | คอลัมน์ | index | เขียนเมื่อ |
| --- | --- | --- | --- |
หรือ: ไม่ลง DB เก็บใน ServerState และ Player(src).state หายเมื่อออกเกม

## state
- ServerState, PlayerState, key ของ state bag (key เล็ก แยกกัน)

## UI
- สไตล์ 1nfx: คัดลอก theme token ฟอนต์ และเสียงคลิกจาก UI [1nfx] ที่ใช้อยู่จริง ไม่สร้างธีมใหม่
- NUI { action, data }, handshake uiReady, cb ครั้งเดียวทุกทาง, ปิดด้วย ESC, ย่อขยายด้วย --px
- action: open, update, close

## network ที่ 1,600 คน
| ข้อความ | ผู้รับ | ครั้งต่อวินาที | ขนาด | ข้อความต่อวินาทีรวม |
| --- | --- | --- | --- | --- |

## ล้าง
- onResourceStop: points, zones, blips, entity, DUI, NUI focus, text UI
- playerDropped: ทุกตาราง [src]

## ทดสอบในเกม
1. <การกระทำ> -> <ผลที่ต้องเห็น>

## นอกขอบเขต
- <สิ่งที่ไม่ทำรอบนี้>
```

กติกา NUI และ DUI ละเอียดอยู่ที่ไฟล์ `NUI_DUI.md` ของ infrontofx

## งบ network ที่ 1,600 คน

คิดเป็นตัวเลขก่อนเขียน: ข้อความต่อวินาที = ครั้งต่อวินาที × จำนวนผู้รับ

| แบบ | ข้อความต่อวินาที |
| --- | --- |
| ส่งถึง `-1` ทุก 500 ms | 2 × 1,600 = 3,200 |
| ส่งเฉพาะ 40 คนในโซน ทุก 500 ms | 2 × 40 = 80 |
| ส่งเฉพาะ 40 คนในโซน เมื่อค่าเปลี่ยน (เฉลี่ยทุก 5 วินาที) | 0.2 × 40 = 8 |

- ส่งเฉพาะคนที่ใช้ฟีเจอร์อยู่ (เปิด UI อยู่ อยู่ในโซน อยู่ bucket เดียวกัน) และเฉพาะเมื่อค่าเปลี่ยน ไม่มีคนดูให้หยุดส่ง
- คนเข้ามาใหม่ได้ snapshot ครั้งเดียว ต่อจากนั้นส่งเฉพาะส่วนที่เปลี่ยน
- payload หลาย KB ใช้ latent event และกำหนด bandwidth ต่อผู้รับ
- state bag ใช้ key เล็กแยกกัน ไม่ยัด table ใหญ่ไว้ใน key เดียว
- รายละเอียดอยู่ที่ไฟล์ `skills/common/networking.md` และ `skills/common/performance.md` ของ infrontofx

## ซักตัวเองเงียบๆ ก่อนลงมือ

ตอบจากโค้ดและผล grep ไม่ถามเจ้าของ ข้อที่ตอบไม่ได้และทำให้ของที่สร้างต่างกัน ให้กลายเป็นหนึ่งในสามคำถาม

- [ ] ใครเรียกโค้ดนี้บ้าง ทั้งใน resource และนอก resource
- [ ] client ส่งค่าอะไรมา ถ้าโกงแต่ละค่าได้ ผู้เล่นได้อะไร และ server ตรวจค่านั้นที่บรรทัดไหน
- [ ] ผู้เล่นออกเกมระหว่าง await, resource restart กลางงาน, สองคนกดพร้อมกัน, กดรัว แต่ละกรณีเกิดอะไร
- [ ] ที่ 1,600 คน งานนี้คูณกับอะไร (loop × คน, query × คน, ข้อความ × ผู้รับ)
- [ ] มีอยู่แล้วใน `1nfx_lib`, `1nfx_core` หรือ resource อื่นไหม ระบบที่ซ้ำต้องมีเจ้าของที่เดียว
- [ ] state ไหนต้องถาวร state ไหนหายเมื่อออกเกมได้ และรอดตอน restart resource ไหม
- [ ] ต้องล้างอะไรตอน `onResourceStop` และ `playerDropped`
- [ ] มีทางที่สั้นกว่านี้และผลในเกมเท่ากันไหม
- [ ] จะพิสูจน์ว่าเสร็จด้วยอะไร ถ้าตอบไม่ได้แปลว่าเป้ายังไม่ชัด ให้เขียนเป้าก่อน
